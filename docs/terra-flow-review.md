# Terra flow review

Read-only source review during active implementation. Findings below describe the code observed at review time; line numbers may move as fixes land. No production services were tested.

1. **Admin edit returns an approved event to review.** `src/event-actions.js:64` treated any `event.requestId` as requiring approval, including for an admin. Approve a member's request, then edit and save that event as admin: a new awaiting request is created instead of updating the event. This prevents the required direct admin edit/save flow. Firestore rules for request-backed events must be considered together with the action fix.
2. **Returned request cannot be resubmitted.** `src/event-actions.js:67-70` reset `reviewedByUid` and `reviewNote` on owner edits; `firestore.rules:429-431` required both fields to remain fixed. Admin requests changes with a reason, then the requester edits and submits: the write is denied. Preserve review metadata or make client and rule behavior consistent.
3. **Saving unrelated defaults can change meeting approval.** `src/routes/event-settings.jsx:19` initialized new defaults with `approval: 'immediate'`; `src/event-model.js:24-28` applied that over the meeting-required default. Open new term defaults, change only place or title, and save: meetings can schedule immediately even though the admin did not explicitly change policy.
4. **Existing edits use newer configuration.** `src/event-actions.js:30-44` read current term and template configuration on each proposal save. Edit an existing event after defaults or its template change: its policy snapshot can change, contrary to the requirement that configuration edits affect new events only.
5. **Calendar out-of-window errors appear empty.** `src/routes/calendar.jsx:38-40` handled `getDocs` rejection by setting an empty array. Navigate beyond the live window with a failed read: the view suggests no events instead of showing an error; previously loaded results can also persist while a new read is pending.
6. **Overlapping timed events obscure each other.** `src/routes/calendar.jsx:63-67` placed events with overlapping time ranges in the same grid cells without an overlap layout. Create two meetings at the same time and view the week: one can cover the other.
7. **Next up can choose a later event.** `src/routes/calendar.jsx:173-174` selected the first public upcoming event before the earliest event overall. When an earlier private event and later public event exist, Next up shows the later event.
8. **Calendar views are incomplete.** `src/routes/calendar.jsx:52-55,184-187` offered week and month only and grouped all events outside 06:00–18:00 under “All day and evening.” There was no agenda mode or distinct all-day representation, including on mobile.
9. **Configuration scope is incomplete.** `src/routes/event-settings.jsx` exposed basic type, policy, time, title, place, notes and participants only. Required/optional field configuration, duration, responsibilities and backups, agenda/minutes defaults, version history, Set as default and bulk preview were absent. `src/event-actions.js:108` overwrote configuration records rather than keeping version history.

Verification observed: `node tests/event-model.test.mjs` produced 5 passes and 1 failure. The failing snapshot assertion expected only the original `configSnapshot` fields, while concurrent implementation had added `defaults` and `templateName`; the matching Firestore `snapshotOk` rules also needed review. `npm test` is not configured. These observations are time-specific because implementation was changing concurrently. No browser journey, emulator rules suite, or production verification was completed by this reviewer.
