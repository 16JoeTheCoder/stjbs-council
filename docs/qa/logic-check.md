### Checks that came out clean (so they need no action)

- Plan Q1 (drop `updatedByUid`): correct; the whole feed document is public, so a student email there would contradict the prompt's own rule.
- Manifest: the current manifest has no `id`, so the prompt's "keeps `id`" is wrong in wording only. Chrome derives the identity from `start_url` (`/#/week` becomes `https://host/`), so an explicit `"id": "/"` is the same identity. Safe.
- Ideas vote rule as planned (size ±1, one-sided set difference equal to `{me}`, other difference empty, no duplicates) blocks `[me, me, me]`, replace-one-for-another, and removing others. `Set.difference` and `List.toSet()` exist in the rules language.
- `createTree` and `exportProject` never write `public` or `publicBlurb`, and `changeLead` patches only `leadUid`, `leadUids`, `updatedAt`, so the planned items rule does not break template trees or lead-change batches. Imported template JSON is whitelisted field by field in `toNodes`, so it cannot smuggle `public`.
- Members matrix: president restricted to `hasOnly(name, section, reportsTo, initials, termId, updatedAt)`, VP excluded from advisor documents, self-change blocked: matches the Roles table. Q2 and Q4 are correctly raised; the VP/president asymmetry is the prompt's, not a plan error.
- RSVP id rule `eventId + '_' + me()` cannot be forged onto someone else's document because the suffix is fixed to the caller's email.
- Submissions: `byUid == me() || isAdmin()` works for single reads and for filtered/unfiltered queries; teachers cannot create. Approve batches stay under the 20 access-call limit.
- Hosting without rewrites serves `/app/` and redirects `/app` to `/app/`; the plan's check in M2 is the right test. `.firebaserc` alias `build` and the `firebase use build` note are correct (no `default` alias, so `firebase deploy` needs it).
- Quota facts: free read quota resets at midnight Pacific, which is 14:00 Jakarta while US daylight time runs (until 1 Nov 2026) and 15:00 after. Plan states both. A listener resumed after more than 30 minutes is billed as a new query; the plan states this correctly.

### Checked and found sound (revision 2)

- Delta query `termId == T` plus `touchedAt >= x` is served by `items (termId ASC, touchedAt ASC)` (§5). One equality and one range on a different field needs exactly that composite index; no `orderBy` is required. Documents without `touchedAt` are absent from that index, which is consistent with the snapshot carrying them.
- Every existing item write path can carry `touchedAt`: `createItem`, `updateItem` (assignee path included, because `touchedAt` joins the whitelist), `changeLead` ancestors and descendants (descendant patch today is only `leadUids`; it must add `touchedAt`, and §3 says every item write does), `createTree`, `archiveItem` and its Undo through `commitChunked`. No other file writes `items` (`admin.jsx` only reads for the backup). Assignees keep write access if `touchedAt` is whitelisted.
- No item is ever deleted (rules forbid it), so the delta cannot miss a removal. Archived items arrive through the delta as updates and are removed locally.
- Archive then rebuild, Undo then rebuild and two admins rebuilding at once all stay correct: `at` is the newest server `touchedAt` the store holds, a later change always has a later `touchedAt`, and the 60 s margin covers `request.time` versus commit order. A stale rebuild that overwrites a newer snapshot lowers `at`, so readers fetch a bigger delta; it cannot resurrect an archived item.
- Non-admins cannot write `cache/*` or `public/feed`, and `touchedAt == request.time` stops anyone planting a future `touchedAt` to skew `at`.
- Read budget arithmetic: 30 + 26 + 52 + 50 + 3 + 26 + 20 + 1 = 208, quoted as 210; 210 × 3 × 30 = 18 900; the day's rows add to 27 520, quoted as 27 500.
- Prompt consistency: new listeners stay out of `loaded()`; `initializeFirestore` with persistent cache is the prompt's allowed exception (the multi-tab manager is the owner's Q3 choice); the cache document is a new collection, covered by "add every new collection to the Close term backup" in §3.
